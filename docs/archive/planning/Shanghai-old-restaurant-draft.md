## 1. 本站定位与完成后的体验

已确认任务：**表达不吃辣的偏好 → 请求推荐 → 确认一道菜**。本草案把它展开为一次有来有回的点菜交流：说出需要、听到回应、作出选择、核对结果。

建议地图上显示“上海老饭店 / Shanghai Old Restaurant”，任务副标题为“找一道合口味的菜 / Find a dish you'll enjoy”。设计停留时间约 5–6 分钟，不要求按固定句数或顺序回答。

用户完成后应能回顾三个交流动作：如何说不吃辣，如何问推荐，如何接受一个选择。系统只说明本次任务达成，不宣称用户已掌握这些句子的发音或能独立完成现实点菜。

首版建议采用三道菜的教学菜单，聚焦偏好与推荐；不增加支付、真实价格、多人分账、完整餐厅经营或开放闲聊。店铺视觉为原创教学空间，不宣称复刻真实室内、人员和当日菜单。

## 2. 体验主线与页面组成

推荐路径：地图选店 → 入店看任务 → 告诉店员不吃辣并问推荐 → 查看推荐 → 选择菜品 → 核对 → 上菜与回顾 → 回地图或去梨膏糖商店。

主界面保留同一张餐桌和店员，学习抽屉与订单确认在场景上展开。下表是六种呈现，不要求建成六个独立网页。

| 页面 ID | 内容与布局 | 主要操作 | 进入/离开规则 |
| --- | --- | --- | --- |
| OLD-01 地图卡 | 建筑小图、地点名、任务短句、本站状态 | 进入或继续、关闭 | 新尝试不预填用户偏好或菜品 |
| OLD-02 到店 | 门面到餐桌的短转场、店员招呼、两行任务说明 | 开始交流、返回地图 | 动画可跳过；开始不自动打开麦克风 |
| OLD-03 餐桌交流 | 场景、店员当前话、菜单、已知信息条、输入区 | 说/写/选、浏览菜品、听重播、看帮助 | 交流主空间，后续分支在此发生 |
| OLD-04 学习抽屉 | 当前相关表达、完整双语读音支持、回听 | 听常/慢速、试读、填入、关闭 | 不更改任务状态，关闭返回原焦点 |
| OLD-05 核对选择 | 已选菜大图、口味说明、店员确认句 | 确认、修改；仍可说/写回应 | 所有必要条件满足后才出现有效确认 |
| OLD-06 上菜回顾 | 保存成功后店员呈上菜品，展示本次交流结果 | 重听表达、下一站、回地图、重练 | 重练新建尝试，原结果保留 |

### 2.1 到店任务卡

中文：“你想点一道不辣的菜。告诉店员你的口味，问问有什么推荐，再选一道并确认。”

English: “You'd like a dish that isn't spicy. Tell the server your preference, ask for a recommendation, then choose and confirm a dish.”

任务卡收起后留下“查看任务 / View task”。这段文字描述目标，不自动让“已知信息”出现不吃辣。开始后信息条应是“口味待说明 · 菜品待选择 / Preference needed · Dish not chosen”。

### 2.2 交流主界面

桌面以餐桌、店员和菜单形成三角构图：店员位于中景偏右，前景桌面摆菜单，背景有暖光窗格。下方固定实色交流面板，正文不直接叠在复杂木纹上。右侧可展开菜单或学习帮助，同一时刻只突出一个辅助面板。

手机重排为上方近景店员与部分餐桌、中部当前对话、下方输入。菜单采用可展开三项列表；不要求横向拖动才发现其他菜。键盘打开时场景可收缩，当前问题、文本框和提交保持可见。

菜品卡显示图片、名称、当前语言说明、“本练习中不辣/辣”的文字标签。菜单是可自由浏览的学习材料；点击图片看介绍不等于选择。点击“选这道”先形成本地回应草稿，用户点“提交回应”后才向店员表达。

店员推荐后，用细边框和“店员推荐 / Recommended”标记对应菜；这与“你已选择 / Your choice”是两种不同状态。不能因为推荐了鱼就默认用户已点鱼。

## 3. UI 艺术方向与交互细节

### 3.1 建议美术方案

| 要素 | 本站设计 |
| --- | --- |
| 氛围 | 温暖、细致、有人情味的饭店；木桌、瓷器、窗格与光影建立层次 |
| 建议色彩 | 界面米白 #F7F0E5，深褐文字 #302A24，木色 #976B48，深青绿主操作 #245C52，暗红点缀 #A34F43；具体组合需测对比度 |
| 店员 | 一位原创、表情自然的成年角色；服饰与 Jada 初期声音协调，不套用真实店员肖像 |
| 角色姿态 | 欢迎、倾听、推荐菜单、等待核对、呈菜五种；无需实时口型 |
| 场景层 | 远景窗格/墙面、中景店员/备餐边柜、前景餐桌/菜单/瓷碟；角色、菜品与 UI 可独立更新 |
| 文字 | 核心汉字 24–28px 起试排，注音至少约 16px；菜单名与状态不靠装饰书法承载 |
| 动效 | 入座、指向推荐、菜品选择标记、呈菜；避免蒸汽或背景客人持续争夺视线 |

### 3.2 必须区分的视觉状态

- 浏览中：菜单卡可以高亮焦点，但没有“已选”标记。
- 本地选择待提交：显示“准备回应：我想要…… / Ready to reply: I'd like…”和提交按钮。
- 服务端已理解：订单草稿显示菜品或偏好；处理中不提前显示成功。
- 与目标冲突：保留用户选择，旁边解释“这道在练习菜单里是辣的”；不能悄悄换菜。
- 等待核对：菜品、口味、确认入口集中；菜品图片与摘要一一对应。
- 已完成：只有保存成功后呈菜、盖地点章；无语音也获得同样完成反馈。

减少动态效果时，用静态构图切换和清楚的文字反馈替代转场。菜单、帮助、返回和确认均支持键盘与读屏；推荐状态同时使用文字，不仅改变边框颜色。

## 5. 店员脚本与主流程

下表是音频制作的语义依据，不是最终上海话台词。理解模型只选择下一种动作；店员教学台词从审校后的模板库取用。

| 台词 ID | 触发条件 | 普通话语义稿 | English gloss | 音频策略 |
| --- | --- | --- | --- | --- |
| OLD-N01 | 开始 | 欢迎，今天想吃点什么？ | Welcome. What would you like today? | 1 条整句 |
| OLD-N02 | 先问推荐，口味未知 | 你吃辣吗？ | Do you eat spicy food? | 1 条整句 |
| OLD-N03 | 不吃辣已知，未问推荐 | 想看看菜单，还是听听推荐？ | Would you like to see the menu or hear a recommendation? | 1 条；旁边显示学习目标提示 |
| OLD-N04 | 已询问且偏好适用 | 推荐清蒸鱼，这道不辣。 | I recommend the steamed fish. It isn't spicy. | 1 条整句 |
| OLD-N05 | 用户换选或明确拒绝鱼 | 白斩鸡也不辣，你想选这道吗？ | The poached chicken isn't spicy either. Would you like it? | 1 条整句 |
| OLD-N06 | 有推荐但未选 | 你想要哪一道？ | Which dish would you like? | 1 条整句 |
| OLD-N07 | 指代不清 | 你指的是哪一道？ | Which dish do you mean? | 1 条整句 |
| OLD-N08 | 选择辣味豆腐 | 这道是辣的，要看看不辣的吗？ | This one is spicy. Would you like to see the non-spicy choices? | 1 条整句 |
| OLD-N09 | 存在偏好冲突 | 你想要不辣的，对吗？ | You'd like a non-spicy dish, is that right? | 1 条；此处答“对”只澄清偏好 |
| OLD-N10 | 对鱼/鸡选择进行核对 | 一份［菜品］，不辣。这样可以吗？ | One serving of [dish], not spicy. Is that right? | 鱼、鸡各 1 条完整音频 |
| OLD-N11 | 信息仍不清 | 我还没听明白，可以再说一遍吗？ | I didn't quite understand. Could you say that again? | 1 条，区别于系统网络错误 |
| OLD-N12 | 用户要求重说 | 重播当前问题或核对句 | Replay the current question or confirmation. | 复用原片段，不生成新句 |
| OLD-N13 | 保存成功 | 好的，请慢用。 | All right. Enjoy your meal. | 1 条整句 |

正常四步示例：

1. 用户提交“我不吃辣，有什么推荐？”；同时保存偏好与询问意图。
2. 店员推荐清蒸鱼；用户可说“就要这个”，也可明确选择白斩鸡。
3. 展示对应菜品的完整摘要；用户通过语音、文字或确认按钮回应。
4. 服务端保存完成后呈菜，回顾 E02/E03/E04；确认与重复表达可展开重听。

用户首轮已说明偏好、问推荐并选好菜时，保留全部有效信息；店员可简短给出推荐/说明并进入所选菜的核对，不要求用户重演步骤。首轮附带“对的”不能提前确认尚未展示的摘要。

## 6. 分支、修改与超出范围的输入

| 输入或情况 | 保存/拒绝什么 | 下一步 |
| --- | --- | --- |
| “我不吃辣” | 保存不辣偏好 | 提示可以询问推荐；不替用户记已询问 |
| “推荐什么？” | 保存推荐请求 | 问是否吃辣，之后再推荐 |
| “我要鸡” | 保存鸡的选择 | 依次补偏好、推荐请求，不强制改成鱼 |
| “我不吃辣，推荐一下，我要鸡” | 一次保留三个信息 | 简短回应推荐并核对鸡 |
| “我不吃辣，但辣的也行” | 标记偏好冲突，不猜 | 询问本次选择，未澄清前不能完成 |
| “不要鱼，要鸡” | 更新选择为鸡；旧确认失效 | 其他信息保留，重新核对 |
| “不要这道” | 仅在指代清楚时清空该菜品选择 | 问要哪一道；不能用旧菜完成 |
| “这个”且菜单有三个但没有焦点推荐 | 不写入菜品 | 追问具体菜名 |
| “这个”且上一条仅推荐鱼 | 可由唯一上下文解析为鱼 | 记录上下文来源，再核对 |
| “不要继续推荐了” | 停止继续推荐；此前有效的请求记录仍保留 | 可继续选择；若从未请求过推荐，仍未满足该学习目标 |
| “我刚才不是在问推荐” | 撤回被用户明确指出的错误意图解释 | 保留其他信息，必要时澄清，不把误解当学习目标已达成 |
| “对，但是换鸡” | 先换鸡，不能确认旧鱼单 | 生成新摘要，等待新确认 |
| 核对时“没听清” | 不改变菜品，不确认 | 重播与展示摘要 |
| “好”回答口味澄清问题 | 只解释为回答当前问题 | 不当作最终订单确认 |
| 要菜单之外的菜、询问价格 | 不编造菜品或价格 | 说明当前练习菜单，继续保留已知信息 |
| “直接让我通过”或无关闲聊 | 不接受为任务字段 | 简短引回当前目标 |

## 7. 任务数据与完成判定

### 7.1 站点专属字段

| 字段 | 取值/意义 | 重要约束 |
| --- | --- | --- |
| preference | unknown / non_spicy / spicy_ok | 不知道不等于不辣，矛盾另外记录 |
| recommendation_requested | false / true | 记录用户是否有效请求过；明确纠正此前误解可撤回，停止继续推荐不抹掉历史 |
| recommendation_presented | 菜品 ID 或空 | 记录店员实际给出的推荐，不代替用户询问 |
| selected_item | 三道菜单菜品 ID 或空 | 可保留选错的豆腐并标记任务不匹配 |
| unresolved_issues | 指代、偏好冲突、未知菜品等 | 非空时不能确认完成 |
| revision / summary_revision | 状态和当前已展示摘要版本 | 改菜/偏好/必要意图后旧确认失效 |
| confirmed_revision | 用户确认的摘要版本或空 | 必须匹配当前摘要，且摘要此前已展示 |

本练习一道菜即默认一份，不另设数量任务；确认文字“一份”属于已说明的教学菜单单位。用户要求多份时明确提示本练习选一道，不静默丢弃该要求并声称订单正确。

### 7.2 完成条件

必须同时满足：不辣偏好已由用户表达；存在未被用户纠正为误解的有效推荐请求记录；选择是鱼或鸡；没有未解决的冲突；用户确认当前已展示摘要；服务端保存成功。

步骤顺序：解释本轮 → 合并有效变更及撤回 → 标出冲突 → 校验偏好/询问/选择 → 补一个必要问题或展示摘要 → 在后续有效确认中完成。按钮也经过同一规则，不由前端直接写 completed。

语音失败、离题、回听或查看菜单不会消除已有有效信息。若出现无法解析的修改，保留旧值用于展示，但明确处于“待澄清”，阻止误用旧值完成。

## 8. 音频、ASR 与未来自部署

初期沿用 `qwen3-asr-flash` 识别、`qwen3-tts-flash` + Jada 提前制作示范与台词。实际效果待测；云端模型不标成 Qwen3-ASR-1.7B。具体适配、版本、超时与权限采用[共同约定](Route-drafts-index.md)。

建议本阶段制作清单：

- 本站核心 E02/E03/E04：每句常速、慢速各一条，共 6 个基础片段；组合练习句若增加，单独审校和编号。
- 共享 E01/E05/E12：引用共享库各两种语速，不重复制作站点副本。
- 三道菜名称：各一条常速、一条慢速，6 个词语片段；说明词语示范与整句读法的关系。
- OLD-N01–N11、N13 共 12 个模板键；N10 展开为两条，基础常速音频共 13 条。N12 复用原音频。
- 首版对可重播店员问题先提供正常速度；额外慢速若制作需独立听审，不通过随意改播放速率冒充已审核慢速。

ASR 小样本优先包含“不吃辣”“吃辣”、推荐请求、三菜名称、不要鱼要鸡、含糊“这个”和确认/没听清。关注否定丢失、鱼鸡混淆以及输入顺序；不能只报告总体转写字符错误率。

给 ASR/理解模型的公共上下文只包括合法菜单、当前对话等，不能把期望答案当作用户已经说出的证据。录音经用户提交才上传；回听、取消及修改转写分别记录。

未来自部署 ASR 使用相同音频与金标准比较；TTS 更换后重新生成和审核上述完整片段，不替换旧研究音频。前端依旧使用表达/台词 ID，任务字段与通关逻辑不变。

## 9. 美术与内容资产清单

数量为建议制作范围，不表示资产已存在。

| 资产包 | 最低交付 | 详细要求 |
| --- | --- | --- |
| 地图资产 | 1 个地标，4 种状态样式 | 未开始/进行中/完成/稍后再来；共用状态组件 |
| 门面 | 1 套主画面及手机裁切 | 地名和操作独立排版，不把按钮烘焙进插画 |
| 室内 | 1 套分层场景、桌面与手机构图 | 背景、店员、桌面、菜单/菜盘可独立替换 |
| 角色 | 1 个原创角色、5 个关键姿态 | 脸/手/菜盘比例一致，避免完成时换人或凭空换菜 |
| 菜品 | 3 张同规格菜品图、对应菜单卡 | 鱼、鸡、豆腐辨识清楚；完成复用已选菜图 |
| 道具 | 菜单、瓷盘、筷子、茶杯、餐桌细节 | 装饰不伪装成可操作控件 |
| UI | 菜单、推荐/选择、信息条、核对、回顾组件 | 四组中英/桌面手机关键稿，完整录音/等待/错误态 |
| 动效 | 进店、推荐、呈菜三个片段说明 | 可跳过，减少动态效果静态替代 |
| 音频 | 第 8 节片段及审核清单 | 记录来源与内容版本，未审核片段不上正式构建 |
| 内容 | 任务、菜单、脚本、表达、近似读音、文化卡、替代文本 | 完整双语，注音与谐音逐条审校 |

可选文化卡建议采用情境说明：“在饭店点菜，先说清口味，再听推荐，最后确认选择。试着把自己的需要告诉店员。”英文使用自然等义短文；若后续增加店史、年代或特色菜事实，先核查来源。现阶段不需要以历史知识作为通关条件。

制作顺序：菜单与脚本语义定稿 → 上海话改写和双人审核 → 参考读法与注音/中文近似读音 → TTS 与听审 → 真实内容高保真 → 插画分层交付 → 界面实现。视觉探索可提前并行，但最终排版必须使用真实长度文本。

## 10. 数据记录与研究观察

沿用共同的 session、attempt、turn、内容/模型/规则版本、输入通道、原转写和解释证据。增加本站分析所需内容：

- 偏好和推荐请求首次有效表达所在回合；两者是否一次完成。
- 店员推荐了什么、用户选了什么；是否把推荐误认为自己的选择。
- 指代消解是否依赖唯一推荐，发生过哪些选择修正。
- 选择不符合口味次数、未解决问题、摘要版本及确认来源。
- 菜单查看、表达卡/注音/近似读音、音频常慢速与重播、人工帮助。

日志可派生“完成任务但全程按钮”“尝试语音后换文字”“看过表达卡再提问”等描述。不能由“问推荐按钮被点击”推断用户能独立说出推荐句。

试运行重点观察：用户是否知道需要主动请求推荐；是否区分推荐与选择；英语用户是否理解菜名；中文近似读音是否帮助开口或导致明显误读；双语界面是否为菜单和读音留出足够空间。

## 11. 验收用例

下列输入是测试语义，正式语音测试还需已审核上海话录音；所有完成用例均需最终保存成功。

| ID | 前提与操作 | 必须得到的结果 |
| --- | --- | --- |
| OLD-T01 | 不吃辣+问推荐 → 接受鱼 → 确认 | 三个交流目标满足，鱼的摘要与呈菜一致 |
| OLD-T02 | 全程按钮，先选鸡再补口味和推荐 | 顺序可变，鸡可完成，无语音要求 |
| OLD-T03 | 先问推荐，再说不辣 | 询问意图保留，之后给适用推荐 |
| OLD-T04 | 只说不辣，店员已介绍鱼 | 不把店员介绍当作用户请求推荐 |
| OLD-T05 | 选择辣味豆腐 | 保留实际选择并说明冲突，不完成 |
| OLD-T06 | 确认前“不要鱼，要鸡” | 更新鸡，新摘要，旧确认失效 |
| OLD-T07 | “这个”但无唯一指代 | 追问，不默认鱼 |
| OLD-T08 | 单轮同时给偏好、询问、菜品 | 三项都保留，摘要前的“对”无最终确认效力 |
| OLD-T09 | 核对时“没听清” | 重播，不完成 |
| OLD-T10 | “我吃辣”或偏好矛盾 | 不把含“辣”当作不辣，追问/提示 |
| OLD-T11 | 旧鱼单上点击确认，但另一回合已改鸡 | 拒绝过期确认，显示新摘要 |
| OLD-T12 | 输入新菜但仍有旧选择 | 产生待澄清问题，不能按旧菜完成 |
| OLD-T13 | 英文输入并切至中文再返回 | 任务保持，英语没有中文近似读音残留 |
| OLD-T14 | 只听示范/填入未提交 | 不记录用户已表达目标 |
| OLD-T15 | 保存失败或重复确认 | 不提前呈菜；恢复后只记一次完成 |
| OLD-T16 | 完成后重练/中途返回 | 新尝试独立，原成功不消失，未完成不误计完成 |

另执行共同约定全部通用用例，检查中英文最长菜名、注音换行、菜单读屏顺序、录音异常和手机键盘。

依赖：共用会话/输入/卡片与服务端规则框架优先由南翔验证，本站新增推荐和菜单能力。建议产品/内容负责人整理脚本与审核，设计负责人负责场景与高保真，工程负责人实现，语言审核由两位流利使用者交叉完成；具体人员分配沿用 proposal 后再排期。

审阅重点：三菜的内容规模是否合适；推荐与选择是否足够自然；菜单在主画面里的比重；五种角色姿态及呈菜动作是否达到预期 UI 质量。现有候选写法与音频需后续审校，不影响现在审阅流程和视觉方向。
